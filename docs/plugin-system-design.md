# 按键插件系统设计草案

状态：设计建议，尚未实现。此文不授权刷机或改变设备配置。

## 用户能看到什么

用户安装一个插件，例如「DFJK」「演示遥控」「编程快捷键」，选择连接的 AhaKey，
点击启用。四个键在启用期间执行插件定义的动作。关闭插件或者退出 Studio 后，
恢复接管前的行为。插件包和用户设置可以保存在电脑上，活动接管状态不能跨重启恢复。

第一版每台键盘同时启用一个改变按键行为的插件，避免多个插件争抢同一次输入。
关闭窗口不等于退出应用；明确的停用操作、退出应用、插件故障、连接丢失都结束接管。
不需要用户理解 HID usage、BLE 命令或 EEPROM。

## 现有代码给出的约束

- Runtime 的 `src/input.rs` / `native/macos/InputMonitor.swift` 观察的是固件处理后
  的 HID usage，不是物理开关编号，也不会阻止原输入进入系统。
- master 的 `APP/hardware/psk_multi_button.c` 会先执行已保存的快捷键或宏。
  多个物理键可能产生相同 usage，一个物理键也可能产生多个 usage。
- master SDK 默认关闭；SDK 的物理键回调是设备内的 C 回调，尚不是电脑能订阅的
  临时接管协议。不能仅启用 SDK 宏就声称已经支持电脑端插件。
- master `0x73` 会修改 `key_bund` 并设置 `have_update_custom_data`。
  `save_all_data_to_fram()` 也可能保存这些修改。因此省略 `0x04` 不是可靠的临时方案。
- 当前配置协议没有按键绑定读回。不能假定能够先备份旧配置、退出再写回。

## 组织方式

```text
Studio：选择插件、设置四键功能、显示启用/恢复结果
    │ 已有认证 IPC + 新增插件会话方法
Runtime：验证插件 → 建立临时会话 → 执行/释放动作 → 恢复
    ├─ 插件定义：输入对应什么行为
    └─ 输入/输出 Adapter：具体怎样接管目标键盘
          ├─ 现有 macOS 的设备键码映射（受限）
          └─ 将来的固件临时会话（完整能力，须先实现）
```

插件的 Interface 只表达行为，不暴露连接、系统授权或恢复流程。
Runtime 的会话 Module 集中处理这些复杂性；Frontend 与插件都不直接操作蓝牙、
macOS 映射表或保存固件配置。已有每设备 worker 继续持有硬件连接，不能另外创建
一个插件 BLE owner。永久配置保存与活动插件会话互斥。

## 第一版插件格式

先支持声明式插件：目录中的 JSON 描述按键动作，无须运行插件作者的代码。
先把 DFJK 的启用、组合按键、停用恢复做可靠，再添加可编程插件。

```text
dfjk/
  plugin.json
  icon.png                 # 可选
```

建议的 `plugin.json`（提案格式，当前 Runtime 不解析）：

```json
{
  "schemaVersion": 1,
  "id": "local.dfjk",
  "name": "DFJK",
  "version": "1.0.0",
  "kind": "bindings",
  "bindings": {
    "key1": { "type": "holdKey", "key": "D" },
    "key2": { "type": "holdKey", "key": "F" },
    "key3": { "type": "holdKey", "key": "J" },
    "key4": { "type": "holdKey", "key": "K" }
  }
}
```

`key1..key4` 是插件的四个逻辑输入位，不使用当前配置的 voice/approve/reject/submit
角色名称。动作改变后，输入身份仍然稳定。Runtime 根据动作推导所需能力，
不能仅相信插件自报的兼容性。

用户为具体设备绑定逻辑输入，单独保存在本地 profile 中：

- 已有物理事件能力：明确记录物理键编号，Adapter 统一编号。
- 现有 HID 兼容方式：记录该设备上经用户确认的独立 usage，标记为 `hidUsage`。
  不能伪装成物理编号；遇到组合键、宏、重复来源或无法确认的关系，拒绝启用四键替换。
  模式变化、设备重新连接或来源关系不再可信时停用，不能复用猜测的映射。

`holdKey` 的语义是按下时保持目标键按下，松开时释放；不是发送一次文本或点击。
同时按 D/F 必须同时保持。D 表示键盘键位，不保证所有输入法和布局输出相同字符。
后续动作可扩展为 `shortcut`、`tapKey`、`runtimeCommand`；各 Adapter 只接受确实
支持的动作，不能把不支持的动作偷偷变成近似行为。

## 两种执行方式与能力限制

| 条件 | 能做什么 | 恢复方式与限制 |
| --- | --- | --- |
| 现有固件 + macOS 设备级 UserKeyMapping | 已确认的独立键码一对一替换，例如四个独立来源映射为 DFJK | Runtime 保存旧映射并主动恢复；macOS 不会因为设置程序退出自动撤销 |
| 将来增加固件临时会话 | 按物理键改变功能、阻止原绑定、直接由键盘输出 HID | RAM 中的覆盖表 + 到期自动失效，不修改已保存键位 |

Apple 的 [TN2450](https://developer.apple.com/library/archive/technotes/tn2450/)
描述了 UserKeyMapping 与 IOHIDServiceClient 的键码映射能力。设备筛选应以本机
`hidutil property --help` 与实际服务识别为准。此路径仅做设备映射，不提供任意
程序化拦截；输入监控的系统权限是另一个独立能力。

现有固件路径的恢复细节：

1. 精确选中目标键盘服务，保存每个服务接管前的映射；不能对全系统所有键盘设置。
2. 先写恢复记录，再修改映射并读回验证。安装失败不报告 active。
3. 停用时恢复此前映射，保留其他设备设置；不是简单设置空数组。
4. 独立恢复 helper 观察 Runtime 的生命管道，Runtime 崩溃时仍能尝试恢复。
5. 若映射被外部工具改过，停止会话并报告冲突，不能盲目覆盖外部新设置。
6. helper 自身也崩溃时不能保证即时恢复。保留恢复记录并在下次启动尝试修复；
   状态必须显示恢复失败，不能笼统承诺「任何崩溃都立即恢复」。

现有固件不满足某个插件的能力要求时，应在启用前解释缺少的能力。
不自动改写永久键位，不自动刷固件，也不以观察事件后再补发键码冒充拦截替换。

## 将来的固件临时会话

若要稳定按四个物理键做任意插件行为，建议以后增加一个小型临时会话协议。
这是更新一次键盘程序以增加能力；每次启用插件仍不保存或重刷固件。
现阶段不分配命令编号，实施前须与设备现有协议扩展统一。

- 能力查询明确报告物理事件、临时覆盖、输出报告与会话恢复支持，不能只相信通用 ACK。
- `beginSession` 返回 sessionId、设备启动标识、有效期、当前物理按键状态。
- `installBindings` 安装经过 Runtime 验证的临时动作表到独立 RAM 区域。
  不修改 `key_bund`、dirty flag 或任何持久化路径。
- `renewSession` 续期；正常退出显式结束，断线/租约到期由设备自己结束。
  可先以 500 ms 续期、2 s 到期作原型，实际数值由连接、睡眠与故障实测决定。
- `keyChanged` 附 sessionId、sequence、物理键编号与完整 held bitmap。
  缺帧先同步状态，不重放可能触发重复动作的历史事件。
- 需要动态 HID 输出时提供完整目标按键状态，而非只能点击的 SDK `hid_send_key`。
  所有命令附会话身份，过期会话输出拒绝执行。
- 接管期间原绑定不执行。启用、切换、恢复要在按键释放后完成；故障结束时清除插件
  输出和待执行宏，对仍按住的物理键等到其释放后再恢复普通行为，防止半个按键事件。
- 心跳只在所属应用会话和插件执行健康时续期，不能让失控插件因 Runtime 仍存活而
  永久占用键盘。设备断电重启必定回到原绑定。

对于 DFJK，临时动作表在键盘本地执行，每个按下/松开无需往返电脑。
复杂插件才订阅物理事件，由 Runtime 将动作送回设备执行或调用受控的电脑功能。
电脑不生成系统键盘事件的设备输出路径无需靠辅助功能注入，但仍须处理蓝牙连接权限。

## 会话、输出与冲突

Runtime 对 Frontend 提供小的 Interface：列出插件与兼容性、启用、停用、读取状态。
例如新增 `plugins.list`、`pluginSession.start`、`pluginSession.stop`；状态通过现有
快照和事件机制发布。方法名及格式在实现时定稿，不能改变既有协议含义。

`start` 包含插件 ID、设备 ID、profile 版本与幂等请求 ID。Runtime 先验证绑定、
占用和恢复能力，然后安装，再返回活动 session。失败不得留下无归属的活动映射。
`stop` 幂等，成功必须意味着该 Adapter 定义的恢复验证已完成。

```text
inactive → preparing → active → restoring → inactive
                          └──→ restoring → recoveryFailed
```

会话归属于启动它的 Frontend 连接身份，即使 Frontend 复用外部 Runtime，退出应用
也必须撤销插件会话。不能只依赖 `BundledRuntimeClient` 关闭自己启动的子进程。
IPC 断开结束会话；重连展示结果，不悄悄恢复接管。Runtime 的设备所有权和单客户端
会话所有权不同，多客户端仍可读取状态，但不能争抢活动会话。

按下时锁定来源对应的动作，松开必须释放同一动作。两个来源同时持有相同输出键时，
最后一个来源松开才释放输出。拒绝无界宏；停止会话取消定时器、待执行步骤和所有
会话输出。用户切换插件先结束旧会话，再验证并启用新会话，第一版不使用隐式优先级链。

## 可编程插件的后续扩展

保持「事件输入 → 返回动作」的 Interface，插件不能持有系统键盘或蓝牙连接。
插件事件包含会话、输入身份和单调时钟，返回的动作经过 Runtime 验证后才执行。
按键时序不经过 Frontend IPC、UI 线程或磁盘日志。

初期只有内置动作与声明式 JSON。确有脚本需求后，新增受监督的独立执行进程，
通过有版本的消息协议承载事件/动作；限制队列、输出长度与执行时间，超时结束会话。
进程隔离只隔离崩溃，不自动构成安全沙箱：未经限制的本地程序仍可能访问用户文件和
网络。第三方可执行插件的隔离方案必须另行完成，不能用一份 permissions 清单冒充限制。
第一版不加载动态库、不下载执行插件代码，也不引入插件商店、依赖解析或自动更新。

## 实施顺序与验收

1. 声明式格式、动作验证与 DFJK 示例；模拟输入覆盖同时按键、重复输出、切换与松开。
2. 会话 Module 和 Frontend 的启用/停用状态；模拟应用退出、外部 Runtime 复用、
   重复请求、安装中失败、插件切换与恢复失败。
3. 验证真实键盘的四个来源。现有固件只启用可证明兼容的设备级映射，并验收恢复 helper。
4. 若现有固件无法满足目标，报告明确限制；用户决定是否实施并升级临时会话固件。
5. 完整路径验收包含：四键并按、长按、插件退出、Studio 强制退出、Runtime 崩溃、
   睡眠/唤醒、蓝牙断线、设备断电、租约到期、旧会话迟到命令、原宏残留和恢复后的首个按键。

目前只有设计文档；没有实现插件加载、临时接管、固件协议或真机恢复验证。
